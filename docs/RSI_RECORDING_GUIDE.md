# RSI 持续修改记录怎么读、怎么用

主文档：[RSI_ITERATIONS.md](../results/RSI_ITERATIONS.md)。它已经补录旧的四组实验和首轮真实模型规则修复试验；以后追加新条目，保留被拒绝的尝试和失败证据。原案例入口：[demo_archive/README.md](demo_archive/README.md)。

## 一一对应的内容

| 项目 | 记录方式 |
|---|---|
| 谁在修改 | Meta 的 Agent 名称、模型配置名、当时的 Worker Snapshot ID；旧数据缺失时明确标注 |
| 修改什么 | Task、Meta 自身、影子 Task、独立规则试验分开；每个实际改变的文件单独一项 |
| 版本关系 | 差异比较起点、候选 ID、实际 Snapshot 父节点分别记录。修复可能与原候选共享父节点，不能把它们误画成父子 |
| 代码改在哪里 | 文件路径、组件、新增/修改/删除和真实 diff；原代码保存在父快照，历史示例保留原路径 |
| 为什么修改 | 机器逐文件声明的理由及它引用的学习案例 ID。保留原始完整说明，理由仍待验证 |
| 实验说明什么 | 诊断预测、控制器实际执行结果、有效性/退步数及修复检查，另开条目 |
| 是否采用 | 后续审计、修复决定和 Meta 换版决定通过相同候选 ID 关联；提出修改不等于已采用 |

条目 ID 示意：`运行目录/00007-code_change.1` 表示某个机器修改事件的第一个文件。后续 `audit`、`repair`、`meta_decision` 等条目携带同一候选 ID，可追踪其去向。普通 Task 优化不自动算作 Meta 改进；影子 Task 仅供比较 Meta，不直接进入正式 Task 演化。

旧实验大多只有整段机器说明，没有逐文件理由。补录时写“未单独记录”，不把人工注释当作机器理由。新调用会要求机器在原有回复中附加：

```json
<CHANGE_REASONS>{"files":[{"path":"middleware/example.py","reason":"具体为什么这样修改这个文件","evidence_task_ids":["实际使用的学习案例ID"]}]}</CHANGE_REASONS>
```

每个新增、修改或删除的文件应只出现一次。缺失、重复或引用未改文件会在日志中保留缺口，原回复不丢失。日志生成本身不增加模型调用；模型输出逐文件理由会占用其原有回复的一部分 token。模型栏是配置名，服务端实际回执应另查原始调用记录。

## 新运行会怎样记录

1. `meta_harness`、`ca_rsi` 和 `recursive_ca_rsi` 在每次产生代码修改或决定时，立即向运行目录中的 `RSI_ITERATIONS.md` 追加。原始脱敏事件同时保存在 `trajectories/`；快照保存在 `snapshots/`。
2. 使用 `scripts/run_experiment.py` 正常完成运行后，会自动将新事件追加到演化展示页同目录的 `RSI_ITERATIONS.md`。默认新展示页为 `results/evolution-live.html`，总日志为 `results/RSI_ITERATIONS.md`。旧的 `evolution-view.*` 演示文件受覆盖保护，不会被新运行刷新。如果把展示页输出到其他目录，日志也随之放在那里。
3. 中断或失败运行已经发生的事件仍在其运行目录。可手动导入未完成运行，不需要模型，也不需要等到最终评估：

```bash
.venv/bin/python scripts/record_iterations.py \
  --run runs/YOUR_RUN_DIRECTORY \
  --output results/RSI_ITERATIONS.md
```

反复导入不会重复追加。相同事件身份对应的原始内容若被修改，导入会报错保留旧记录；需另写带新身份的更正记录。不要改掉旧条目后冒充最初的判断。

直接调用 FlashRSI 的其他入口也会生成运行内日志；汇总到仓库总日志可使用上面的导入命令。日志自动记录后续实际发生的运行，本功能不会自行启动新的付费实验。

## 本次接入的规则验证

新增示例配置：[recursive_ca_rsi_rule_audit.yaml](../configs/recursive_ca_rsi_rule_audit.yaml)。旧配置和旧实验都保留原样。新配置将 Meta 固定，并开启：

```yaml
algorithm:
  rule_verification: true
  max_rule_cases: 4
  meta_self_update: false
```

确定性答案处理中间件须导出同模块的 `AUDIT_RULES`，并通过 `ctx.apply_answer_rules(answer, evidence, AUDIT_RULES)` 执行。真实运行记录模块路径、源码哈希、原始输入、证据和输出，外层绑定 Task 快照与任务 ID。

当前实际流程是：

1. 在公开学习任务上运行候选，保存最后一次成功答案处理的原始边界。早前重试中的中间结果不冒充最终输出。
2. Meta 先提交诊断和可选的结构化 `interventions`：案例 ID、关闭规则 ID、预期精确输出、机制假设。
3. 固定控制器在独立进程加载候选快照，执行所有不超过四规则的组合，各重复两次。首先必须重现存档的完整规则输出。随后由外部已有 Benchmark 重新评分；占位评分不进入结论，参考答案也不作为规则输入传入。
4. 将执行结果交给原有的修复调用，不另加一次模型反思调用。Meta 提出修复后，对同一批冻结输入重放。
5. 修复仍须通过原有完整学习任务的净收益/退步门槛；可比较的规则边界还要求执行有效且不引入新的退步。通过学习检查后，仍需后续新审计题决定是否真正采用。

只有已声明的纯转换进入该机制。当前最多采集 16 个案例，示例配置为 4；规则重放进程各有 15 秒上限。无法重放、源码/快照不符、输出不能重现或主评分不是二元值时，会记录“不可用/不支持”，不会假装机制已验证。当前还不支持一般检索、模型重试、规划或多轮推理的机制干预；纯函数也是接口约定，子进程不构成恶意代码安全隔离。

`rule_intervention` 记录来自已经可用的学习任务，后续 Task 提案和 Meta 自身修改可以读取已完成的验证记录。未来审计题、Meta 专用新挑战及最终测试不会因这个接入而提供给修复器。
