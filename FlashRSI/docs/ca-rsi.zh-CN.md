# CA-RSI：候选修改的反事实审计

CA-RSI 沿用 Meta-Harness 的文件编辑 Worker，但从当前已选中的 Snapshot
提出下一轮候选。它把候选相对当前版本改变的每个文件视为一个修改单元，
评测原版、完整候选和所有可组成的文件子集，然后选择开发集得分最高的
合格子集。同分时保留修改文件更少的版本。

## 数据边界

- Worker 只看到训练题的执行轨迹、自己的历史消息和历史 Snapshot 源码。
  审计题的输入、输出、分数与选择记录不会进入它的历史目录。
- 开发题按固定顺序交错分给各轮，同一道开发题只用于一轮审计。
  每轮用同一批题比较当前版本及其全部候选子集。
- 已用过的审计题会成为保留集。后续轮次先按新题排序，再检查拟选
  子集是否使保留集退步；不合格则尝试下一个子集。
- 测试题由 FlashRSI 在演化结束后评测，不参与修改或选择。
- `train` 必须非空，且训练题与开发题的 task ID 不得重叠。

## 选择与记录

配置 `max_edit_units` 默认为 3，最多可设为 4；超过预算的候选跳过。
因此一次审计最多需要 16 种版本的新开发题评测，包含原版和完整候选；
多轮运行还会增加保留集评测。
只有得分严格高于当前版本、且逐题退步数不超过
`max_task_regressions` 的子集才可被选中；同一门槛也用于保留集，
默认允许 0 道退步题。
审计记录保存在运行目录的 `trajectories/*-audit.json`，其中包含每种
版本的 Snapshot ID、修改文件、总分、逐题分差、退步数、删除单项修改
后的条件贡献，以及最终选择。无法独立组合的子集会记录为无效。

`leave_one_out` 是“完整候选分数减去删除这一文件后的分数”。它只是该
组合和这批题上的条件比较；交互效应、抽样噪声和未测试任务仍可能改变
结论。一个文件中的多个语义修改目前不能分开归因；研究实验应要求
Worker 尽量把独立想法放在不同文件，或进一步实现结构化补丁清单。

## 运行

从 `examples/ca_rsi_hotpotqa.yaml` 开始，填入可用的 Target/Worker 模型、
API 凭据和必要的端点，然后运行：

```bash
flashrsi run --config examples/ca_rsi_hotpotqa.yaml
```

示例中的 8/16/16 题只用于检查流程。正式实验应扩大每轮开发题和最终
测试题，并固定模型版本、温度、数据划分与调用预算。在相同预算下比较
原版 Meta-Harness、只保留完整候选、逐项贪心选择和 CA-RSI；至少再用
一个数据集复验，并报告最终成绩、有害修改保留率、逐题退步与调用成本。
